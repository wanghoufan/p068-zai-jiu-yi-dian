## 1. 差距证据链

### 差距 D1｜「按组计次」模式从无到有，三 Tab 结构被推翻为四 Tab

1. **原来怎么说**：`docs/plan/P068-Android-Development-Plan-V1.2.md`（2026-11-05 落盘）§2.2 明确「三个一级 Tab（顺序不可变）：训练 / 历史 / 设置」，§1 Constitution 第 1 条定义为「通用时长进阶工具」；全篇无任何「次数/组数/RepSet」概念。
2. **后来实际怎样**：2026-11-06 一天内两轮返工——先出 V1.1 三 Tab 计划（`P068-Android-Dual-Mode-Training-V1.1-Approved-Plan.md` 行 31 明文「不新增第4个底部 Tab」），同日被用户推翻，改为四 Tab 最终计划（`P068-Android-Dual-Mode-Training-V1.1-R2-Final-Approved-Plan.md` 行 8–11 记录了完整审批链：用户「反馈双模式必须在同一个 APP 内呈现独立训练入口，最终明确底部四 Tab」，并「明确反对把旧历史页简化」）。实现落地为 `ui/screens/RepsScreen.kt` + Room v2（`AppDatabase.kt:18` version=2，`AppDatabase.kt:29` MIGRATION_1_2），交付 1.1.0（versionCode 3）。
3. **差在哪里**：不是「做错了」，而是「原来根本没这一块」。差的层级有三：①导航结构（三 Tab→四 Tab）；②数据模型（sessions 只有秒数字段，计次需要 rep_sets/rep_draft 新表 + mode 字段，且「绝不能把次数填进秒数字段」，V1.1 计划行 15）；③备份格式（V1/V2 无法装组明细）。
4. **为何本应提前思考**：需求对象是「平板支撑、静蹲等健身/训练」（V1.2 计划 §2.1 用户画像白纸黑字写了「可能在健身/专注练习中」）。任何一个有经验的计划者面对「健身训练记录工具」这个命题，第一组标准问题就是「你的训练分两类：计时类（平板支撑）和计次类（俯卧撑、引体向上），你两个都练吗？」——计次是训练类 APP 的另一半基本盘，属于领域常识，不需要用户先开口。
5. **不提前会造成何种返工**：①V1.1 第一版计划与配套方案整体作废重写（三 Tab 版在 R2 Final 计划行 6 被明文标注「已过时……不再作为最终 UI 真源」）；②Room v1→v2 显式迁移 + 两台真机旧库迁移实测（HANDOFF §1「两台旧设备 install -r 后旧项目保留」）；③备份 V3 整套编解码 + V1/V2 兼容校验（BackupCodec.kt:308 版本分支）；④导航、数据、备份、统计四层同时动。一天内连发 3 份计划文件（V1.1 Approved → V1.1 R2 Final），用户同日两次拍板。
6. **下次普通人怎么说**：「我这个训练里，除了掐表计时，引体向上这种是不是还要一组一组记次数？」
7. **提前明确的收益**：Room 首版即可带上 mode/rep_sets（建表比改表+迁移便宜一个量级）；备份 schema 第一版就能兼容两种模式，V2→V3 两次扩展可省掉一次；V1.1 计划不会写完即废。省掉的是「同一天两轮计划返工 + 一次真机迁移实测」。

### 差距 D2｜锁屏/后台语音提醒：前台能响 → 后台哑火 → 前台服务补课

1. **原来怎么说**：V1.2 计划 §2.4 时间技术合同（行 114）只写了「若要锁屏下准点系统提示，先验证 AlarmManager/通知权限……不以长期不受限的后台服务为前提」——把锁屏提醒定位成待验证的可选项，没有进任何 AC。
2. **后来实际怎样**：V1.0 QA（2026-11-06）「未验证/已知限制」第 1 条自认「V1.0 未实现锁屏/后台响铃……这是能力缺口」；随后用户点名三项增强（`P068-Android-Reliability-And-Acceptance-V1.0.1-R2.md` 行 6：「用户明确要求把【自动本地备份、锁屏/后台语音提醒、可见备份回滚入口】三项加入本次开发」），R2-T04 用 `specialUse` 前台服务 + 常驻通知 + PARTIAL_WAKE_LOCK 实现（`TrainingForegroundService.kt:72`）。
3. **差在哪里**：产品宪法第 5 条自己写着用户场景是「健身/专注练习中单手操作……能锁屏」（V1.2 计划 §2.1），锁屏后没声音直接击中主场景；但 AC-01～AC-19 没有一条要求后台播报。
4. **为何本应提前思考**：计划者写画像时已经知道「锁屏使用」，却没有把画像翻译成验收条款——「画像里有锁屏，AC 里没有锁屏」是同一次计划内的自相矛盾。当时能想到：只要产品声称「训练时能锁屏」，锁屏提示就是 P0 候选，至少该问用户「锁屏后还要它报时吗」。
5. **不提前会造成何种返工**：整个 R2-T04 任务（前台服务类型选型、Android 11/14/15 权限矩阵、通知降级、锁屏节点去重）都在 V1.0 交付之后追加；连带 QA 证据重做（25:53 真实长训练、锁屏节点观察）。
6. **下次普通人怎么说**：「手机一锁屏它就没声了，我练平板支撑根本不看屏幕，锁屏了也得提醒我。」
7. **提前明确的收益**：前台服务选型与权限降级一次做进 V1.0，省掉整个 R2-T04 迭代和一轮三机重验。

### 差距 D3｜开始/每 3 分钟语音反馈：验收现场追加，且中途换实现方案

1. **原来怎么说**：V1.2 计划 §2.3 设置页只写「提示音/震动」，无「开始要有反馈」「每 3 分钟报时」任何字句。
2. **后来实际怎样**：V1.0 验收矩阵「用户追加需求验收（2026-11-06，非原计划 AC）」F-01/F-02（`产品验收追踪矩阵-P068-V1.0.md` 行 45–48）——用户在真机体验时当场提出，当天实现；`agent.md` 行 23 记录了「语音提示依赖系统 TTS → 系统 TTS 引擎与中文包因机型而异 → 改用本地 WAV + SoundPool（参考 P045）」的方案切换；最终 36 个 WAV 资产（`architecture-facts.md` §2，约 3.2 MB）+ `tools/make_voice_cues.sh` 可复现生成。
3. **差在哪里**：交互反馈密度（何时响、响什么）完全没进计划；实现选型（TTS vs 预生成 WAV）也走了弯路。
4. **为何本应提前思考**：训练是「不看屏幕」的活动（与 D2 同根），提示节奏是核心体验；P045 项目已经验证过本地 WAV + SoundPool 方案（agent.md 行 23 原文「参考 P045」），跨项目经验当时就摆在那里。
5. **不提前会造成何种返工**：TTS 方案中途废弃重做；36 个语音资产补录 + 生成脚本；R2 又把播报逻辑从 UI 层搬进前台服务（换宿主）。
6. **下次普通人怎么说**：「点了开始我得有反应——响一声或者说句话；每练满 3 分钟报一下，不然我练着练着忘了看时间。」
7. **提前明确的收益**：直接按 P045 模式出 WAV 方案，省掉 TTS 试错；提示节点表（开始/3 分钟/达标）一次写进 AC，不用验收现场加塞。

### 差距 D4｜备份格式：V1→V2→V3 三级扩展，每次都在追着数据结构跑

1. **原来怎么说**：V1.2 计划 §2.8 设计了 `BackupMeta: schemaVersion`（行 159，说明「支持以后迁移」的意识在），§2.9 定义备份内容为「项目、目标、预设、历史、备注、设置、删除标记、schemaVersion」。
2. **后来实际怎样**：V1 备份的 settings 只含 theme/soundEnabled/vibrationEnabled（V1.0.1-R2 计划行 18 核实「当前『完整备份』没有全部用户设置」）→ R2-T01 出 V2 补 voice/font/range/chart/filter → V1.1 出 V3 补 mode/计次计划/每组 sets/草稿/lastTime/lastReps（`architecture-facts.md` §3 备份 schema 条；`BackupCodec.kt:308` 版本分发）。V1/V2 仍按各自原算法校验兼容。
3. **差在哪里**：①V1 的「设置」定义窄于实际 DataStore 保存的设置（写代码时两边清单没对齐）；②没有任何机制阻止「新增业务数据但忘记进备份格式」——计次数据若晚一版进备份，用户拿旧 V2 文件恢复会永久丢组明细（`risks.md` R11 已如实记录该风险）。
4. **为何本应提前思考**：schemaVersion 的存在说明设计者预料到会演进，但缺一条制度：「每个会落库的新实体，当天必须在备份编解码里有对应字段，否则不许合入」。这条纪律不需要预知未来需求，只需要一个对账动作。
5. **不提前会造成何种返工**：BackupCodec 三轮扩展 + 每轮 V1/V2 兼容单测重写；V3 恢复后 KPI 变 0 的 P0 缺陷（agent.md 行 31：恢复时子表 rep_sets 未回填）；以及 R11 留下的长期隐患（旧备份恢复不出计次数据）。
6. **下次普通人怎么说**：「我换手机把备份导进去，昨天引体向上做了几组几分几秒，能不能一条不差全回来？」
7. **提前明确的收益**：若 V1 就把「备份字段清单 = Room 实体清单」做成对账检查，V2、V3 两次扩展至少可以合并成一次（设置遗漏与计次一次补齐），单测少写两轮。

### 差距 D5｜统计口径：时长单口径 → 双口径 + 「全部项目」防混单位

1. **原来怎么说**：V1.2 计划 §2.7 全部指标（平均时长、达标率、散点、分组表）以秒/分钟为唯一单位。
2. **后来实际怎样**：R2 Final 计划 §2.3（行 56–59）要求「时长用秒/分钟，次数用单次真实总次数……选择全部项目时只能展示共同口径（如训练次数/训练天数），不能在单一『平均成绩』里混合两个单位」；实现落为 `Stats.kt:61` `activeDays` 与混合口径隔离，真机证据 `evidence-v11/09-history-mixed.png`。
3. **差在哪里**：原口径体系没有「多模式」概念；且分钟与次数相加是语义错误，不是精度问题。
4. **为何本应提前思考**：这是 D1 的下游——计次模式进了数据层，统计口径必然要分叉。若 D1 在立项时解决，本项自动消失，不构成独立差距。
5. **不提前会造成何种返工**：Stats/图表/关系表全部按模式分支重写一遍；「全部项目」视图重新设计为只合并次数/天数。
6. **下次普通人怎么说**：「我既有计时项目又有计次项目，一起看的时候别把分钟和次数加在一起给我个四不像的平均数。」
7. **提前明确的收益**：随 D1 一并消化，无独立收益账。

### 差距 D6｜字体偏小与字号档位：真机上手才暴露

1. **原来怎么说**：V1.2 计划 AC-17（行 236）只写「窄屏和大字体下底部导航/主按钮不遮挡」——是对「不遮挡」的负向要求，没有「默认够不够大」的正向要求。
2. **后来实际怎样**：V1.0 QA 缺陷 7「字体偏小（用户追加需求，已实现）」（QA-REPORT-V1.0 行 63）：应用内字体 100/115/130/145%，默认 115%，即时生效并持久化。
3. **差在哪里**：计划假设「系统字体默认值=用户可接受」，没有问目标用户（健身场景、手臂前伸、汗手）需要多大字。
4. **为何本应提前思考**：用户的另一项目规则里本就有界面字号下限的全局偏好；且训练场景看屏距离远，属常识。此条一半可预防（问一句「大数字够不够大」），一半是主观感受必须真机确认。
5. **不提前会造成何种返工**：字号档位系统（含持久化、与系统字体叠加）在 V1.0 验收期追加，主题层与备份 V2（fontScalePercent 进备份）连环改。
6. **下次普通人怎么说**：「我在瑜伽垫上隔着一步远看手机，倒计时的数字再大一档。」
7. **提前明确的收益**：档位系统进 V1.0 首版，备份格式第一版就带 fontScale，少一次 V2 扩展。

### 差距 D7｜自动本地备份与可见回滚：计划里的「非阻塞增强」被用户升级为必做

1. **原来怎么说**：V1.2 计划 §2.9（行 172）：「自动本地备份是可并行完善的非阻塞增强，不能以未实现自动备份否认手动恢复已通过」；V1.0 矩阵「已知边界」第 2 条据此判定不阻塞。
2. **后来实际怎样**：用户点名三项增强之一（R2 计划行 6），R2-T02/T03 实现 SAF 目录持久授权、1.2 秒合并、写后回读校验、7 版轮转（`AutoBackupManager.kt:310` MAX_AUTO_BACKUPS=7）、`zjyd-safety-*` 保护点、可见回滚列表。
3. **差在哪里**：计划把「手动备份恢复」判为硬验收、把「自动备份」判为可延后——技术上没错，但低估了用户对「忘了导出就丢数据」的担心程度；数据安全需求从「能用」被用户抬到「不用惦记」。
4. **为何本应提前思考**：计划者可以合理分级，但应在计划里显式问用户一句「自动备份你要不要算进首轮必做」，把分级变成用户决策而不是开发者假设。
5. **不提前会造成何种返工**：不算高代价返工——R2 的 SAF/轮转/回滚本来就是设计好的方案，只是整体后移了一轮；主要代价是 V1.0 的「完成」声明带着一个用户眼里的大缺口。
6. **下次普通人怎么说**：「我懒得每次手动导出，它能不能自己定期把数据备到一个文件夹，我还得能看到备份了哪几版。」
7. **提前明确的收益**：有限——此项属于「计划判断基本合理、用户优先级不同」，归类时按正常迭代处理更公平。

## 2. 责任归属三分

| 差距 | 用户合理应表达 | 顾问/计划者应主动发现 | 开发者负责解决 | 归类依据 |
|---|---|---|---|---|
| D1 计次模式 | **是**（练引体向上是他的真实生活，只有他知道） | **同为是**（健身工具的两大基本模式属领域常识，计划者面对「健身/训练」画像应当主动问出这一问，而不是等用户想到 APP 还缺一半） | 数据层/迁移/备份实现质量 | 双主责：用户没说 + 计划者没问。计划者责任不低于用户——「该问的问题没问」正是顾问职业价值所在 |
| D2 锁屏语音 | 部分（「锁屏也得提醒我」一句即可） | **主责**（计划自己写了「能锁屏」的画像，AC 里却没有锁屏条款，属于画像→AC 的翻译遗漏） | specialUse 选型、权限降级、OEM 差异处理 | 计划者责任为主：信息全在自己写的文档里，只是没接上 |
| D3 开始/3 分钟反馈与 TTS 选型 | 部分 | **主责**（提示节奏是训练工具核心体验；P045 的 WAV 方案是现成跨项目经验，计划者应带进新项目） | 实现与资产制作 | 计划者责任为主：跨项目经验未复用是流程问题 |
| D4 备份三级扩展 | 否（用户无法表达 schema 对账问题） | **主责**（缺「实体清单=备份字段清单」对账制度，属方法论缺口） | V3 KPI 回填缺陷等实现 bug | 计划者/开发者共同：制度缺口是计划层，回填 bug 是实现层 |
| D5 统计双口径 | 否（下游问题） | 随 D1 | 实现 | 派生差距，不独立追责 |
| D6 字号 | 部分（「数字再大点」很自然） | 部分（训练场景远距看屏是常识） | 实现 | 均摊：主观感受类本就依赖真机反馈，不算重大失误 |
| D7 自动备份 | 是（「我要自动备份」只有用户能定优先级） | 部分（应显式抛给用户而非自判「非阻塞」） | 实现 | 用户主责：优先级决策权在用户，计划者仅少问了一句 |

**小结**：七项差距中，计划者应主动发现占四项主责/半主责（D1、D2、D3、D4），用户应表达占两项主责（D1 并列、D7），纯实现问题（FK 崩溃、Mutex 死锁、暂停计数等）全部归开发者（见 §3/§4）。把 D1、D2 这类最大返工归给「用户没说」是不成立的——用户画像与领域常识早已把答案写在计划里。

## 3. 返工分类

### 3.1 可预防返工（当时多说一句话就能避免）

1. **TTS→WAV 方案切换**（agent.md 行 23；QA-V1.0 F-01/F-02 说明）：P045 已验证本地 WAV + SoundPool，开工时复用跨项目经验即可一步到位。
2. **V1.1 三 Tab 计划整体作废**（V1.1-Approved-Plan 行 31「不新增第4个底部 Tab」→ R2-Final 行 8–11 被推翻）：写计划前先问清「新的训练类型要不要独立一级入口」。
3. **撤销窗口 2.7 秒过短**（QA-V1.0 缺陷 3）：UX 常识阈值（Android 惯例 snackbar 时长下限之上的可操作性），一次评审可拦住。
4. **结束动作被计成暂停**（QA-V1.0 缺陷 2；agent.md 行 21）：`requestFinish` 复用暂停路径，代码评审按状态机走查即可发现「结束不应改暂停计数」。
5. **种子预设单位错误**（QA-V1.0 缺陷 4，15/20/25 分钟被当秒）：数据进场先跑格式化断言即可拦住。

### 3.2 正常迭代（真实世界的不确定性，事后不该被指责）

1. **计次模式本身的出现**：用户需求随真实使用浮现（先有平板支撑、后有引体向上），立项时用户未提及不算过错——但计划者本可问出来（见 D1 双主责定性；这里指「出现需求」这件事本身不是错）。
2. **MIUI「USB 安装」自动关闭**（agent.md 行 20）：厂商 ROM 行为，无文档预警，只能踩过才知道。
3. **SAF 文件夹名被输入法打乱**（agent.md 行 27）：系统文件选择器 × 输入法 × 脚本注入的交互，属验收环境噪声，且已正确标 NOT_RUN 未冒充通过。
4. **验收中其他应用抢占前台**（agent.md 行 34）：共享测试设备的环境干扰，处置正确。
5. **Gradle Kotlin DSL 缓存损坏**（agent.md 行 24）：可再生基础设施问题。
6. **真机无 sqlite3 / WAL sidecar**（agent.md 行 33）：Android 平台碎片化的常规发现。
7. **字号默认值不合手感**（D6）：主观感受必须真机定标。
8. **自动备份优先级后移**（D7）：分级判断技术上合理，用户权重不同。

### 3.3 Agent / 流程失误（本可做好但没做好）

1. **锁屏语音原始 logcat 被重装清空**（agent.md 行 28；QA-V1.0.1-R2「未验证」第 3 条）：观察到关键节点后未立即导出证据，重装动作在其后执行。取证纪律已有章法（观察→立刻落盘），执行顺序错了。
2. **多机推送首轮只看 install Success**（agent.md 行 22）：V1.0 QA 明明已建立「回读 base.apk SHA-256」的正确做法（QA-V1.0 §5.1），后续某轮却退回只看返回码——不是知识缺口，是流程回退。
3. **推送清单漏掉后连设备**（agent.md 行 29）：未先列目标机型清单再对照 `adb devices -l`，按当下返回值即行动。
4. **「空间不足」被写成现状**（agent.md 行 30）：把计划中的模拟故障场景写成事实陈述，报告口径失守，还引发用户追问。
5. **恢复类操作两次子状态缺陷**（Mutex 不可重入死锁 agent.md 行 25；V3 KPI 变 0 行 31；恢复后项目短暂为空 行 26）：共性是「覆盖/回填内存状态时未带齐全部关联状态」。三条同根，若第一次死锁修复时就沉淀「恢复=事务+全量回填」检查单，后两条可避免——同类缺陷在一天内出现三次，属流程未及时收敛。

## 4. 根因追溯（四类问题追到底）

### 4.1 UI/交互类

- **现象群**：四 Tab 结构返工、NextSetCard 改计划后建议值不更新（agent.md 行 32）、撤销窗口过短、字体偏小。
- **根因**：①需求启发缺失——项目有「获批 HTML 原型」这道很强的工序，但原型的输入只有用户已经说出的场景（平板支撑计时），原型工具再好也放大不了没被说出的需求（D1 链）；②状态派生遗漏——`NextSetCard` 的 remember key 只含组号不含 nextReps，属「输入源变化未触发重建」的 Compose 通用陷阱，根因是修改计划的代码路径无 UI 测试覆盖；③UX 阈值无标准——撤销时长、字号默认值靠当场拍脑袋。
- **可预防 / 正常迭代 / 流程失误判定**：需求启发缺失=可预防（一句话提问）；remember key=正常迭代边缘（单测覆盖后即消失）；UX 阈值=可预防（定内部标准）。

### 4.2 操作体验类

- **现象群**：恢复后项目短暂为空（agent.md 行 26）、V3 恢复后 KPI 变 0（行 31）、改计划建议值不更新（行 32）、键盘/输入法干扰（行 27）。
- **根因**：统一根因是 **Room Flow 异步回填与手动内存回填两套状态源并存**。凡是「写完库以为 UI 会自己变」的地方，都会在「写完到 Flow 重发」的窗口里露出假状态。三条缺陷是同一根因的三次显形；正确姿势（要么完全依赖 Flow、要么同一事务处同步回填全部关联）在第三条之后才沉淀成文（经验一句话.md 2026-11-06 最后一条）。
- **判定**：流程失误（未及时收敛）——第一条发现时就该立规矩，而不是踩满三条。

### 4.3 外部依赖类（Android 权限、前台服务、SAF、TTS）

- **现象群**：MIUI USB 安装自动关闭、SAF 输入法打乱、通知权限拒绝、OEM 省电、TTS 不可控、specialUse 类型合规存疑（risks.md R8）。
- **根因**：①预检矩阵只预检了 **Android 官方限制**（R2 计划 §7 全部是 developer.android.com 链接），没有预检 **OEM 层**（MIUI/HyperOS）——MIUI USB 开关这类行为官方文档不存在，只能靠「拿到机型清单后先跑 5 分钟环境探针」来兜底，而三台 Redmi 机型清单在计划期就已知（E03/E05），探针没做；②TTS 是选型失误而非平台未知：跨项目经验（P045）已在手而未查——归可预防；③specialUse 前台服务类型是 Android 14 新约束下的合理选择但留了上架合规尾巴（R8），属已知边界而非失误。
- **判定**：MIUI/SAF 输入法/省电策略=正常迭代（不可预知，处置正确均标 NOT_RUN 或如实降级）；TTS=可预防；logcat 清空归 §3.3 流程失误。

### 4.4 质量验证类

- **现象群**：结束被计成暂停（主流程截图看不出）、多机推送只看返回码、「空间不足」口径事故、32/32 与 24/24 自动测试均未覆盖上述缺陷。
- **根因**：**验收断言只对齐「用户看得见的 happy path」，未对齐「状态元数据与不变式」**。`pauseCount/pausedSec`、安装后包哈希、KPI 数值这些可机器断言的量，第一轮都靠人眼截图；每次都是真机踩坑后才补断言（经验一句话.md 2026-11-06「真机验收要核对元数据，不只看主流程跑通」）。更深一层：本项目验收由单一主开发者自测自验（HANDOFF §3「无独立 reviewer/qa 角色链（主开发者模式）」），自写自验天然偏向自己的实现假设，「结束=暂停」这类语义混淆恰恰是第二双眼睛最容易拦住的。
- **判定**：流程失误为主（元数据断言与独立复核缺位）；其中单测未覆盖的边界（如 finish 路径不改暂停计数）属可预防。

## 5. 下次立项时的通俗需求表达问题（10 问）

1. 这个训练里，除了倒计时，你还要不要按组记次数？哪些项目是计时的、哪些是计次的？
2. 练的时候你会锁屏吗？锁屏之后还需要它一直报时/提醒吗？
3. 点下「开始」以后，你希望它给你什么反应？（响一声、说句话、还是震动？）
4. 练到多少分钟你想被提醒一次？3 分钟？5 分钟？还是不要打扰？
5. 你打算在离手机多远的地方看数字？现在的倒计时字体大小够吗？
6. 记错了或者手滑删了一条训练记录，你希望怎么补救？（能撤销多久？要不要「最近删除」回收站？）
7. 一天练两次、或者临时把 3 组改成 4 组，历史里应该怎么记——每次都算独立一条吗？
8. 你希望它多久自己备份一次？备份文件放哪你能找到、又不会被别人看到？
9. 换手机的时候，你期望把备份文件导进去之后，哪些东西必须一条不差地回来？（历史、备注、设置、进行到一半的记录？）
10. 你平时用哪几台手机？装测试包的时候，愿不愿意配合重新开一次「USB 安装」开关、选一次备份文件夹？

## 6. 开工前体检表（14 项）

**需求侧**
- [ ] 1. 列出用户真实会做的全部训练类型清单（计时的、计次的、其他），逐条问「这个 APP 覆盖吗」，不按单一样例项目推导。
- [ ] 2. 对每个核心使用场景问一遍「锁屏后呢？」——锁屏/后台行为必须有对应 AC，不允许只活在用户画像描述里。
- [ ] 3. 明确反馈节奏表：开始、进行中（间隔提醒）、达标、结束各给什么反馈（声音/语音/震动），写进 AC。
- [ ] 4. 明确撤销/恢复规则：撤销窗口时长、是否要「最近删除」区、草稿是否持久化，逐条用户确认。
- [ ] 5. 混合单位口径预先声明：多类型数据并存时，哪些指标可以合并、哪些永远分开，用一句用户能听懂的话确认。

**数据与备份侧**
- [ ] 6. 建立对账纪律：Room 实体清单 = 备份格式字段清单，每个新实体合入当天必须出现在备份编解码与单测里，用脚本或清单核对。
- [ ] 7. 备份格式从第一天带 schemaVersion 且写明升级规则；设计「旧版本文件恢复新数据」的用户提示话术。
- [ ] 8. 迁移策略显式化：禁止 destructive migration 写进 CI 断言；每个 schema 版本配一条真实旧库迁移实测。

**真机与环境侧**
- [ ] 9. 机型清单先定：几台、型号、Android 版本、屏幕尺寸，写进计划；每台到手机先跑 5 分钟环境探针（USB 安装开关、SAF 选择器、通知权限、省电策略）再进功能测试。
- [ ] 10. MIUI/HyperOS 专项：确认「USB 安装」开关状态并保持亮屏，把「安装失败先查系统开关」写进操作手册，防误判 APK 问题。
- [ ] 11. SAF 测试用纯 ASCII 短目录名，先 `uiautomator dump` 核对输入框再继续；不可控即标 NOT_RUN，转人工。
- [ ] 12. 取证即落盘：每观察到一个关键节点（语音、崩溃、迁移），立即导出 logcat 到 `docs/qa/evidence-*/`，再执行任何重装/重启。

**验证侧**
- [ ] 13. 验收断言两级制：一级=用户可见主流程截图；二级=状态元数据与不变式（pauseCount/pausedSec/targetSec、KPI 数值、安装包 SHA-256 回读、恢复后子表完整性），二级缺失不得记 PASS。
- [ ] 14. 同类缺陷收敛规则：同一根因的缺陷第二次出现时必须沉淀成检查单/断言，不允许第三次以同样方式出现（本项目「恢复类回填」踩了三次）。
