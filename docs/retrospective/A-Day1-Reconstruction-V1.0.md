## 1. 当前产品真实形态（V1.1.0 实际有什么）

### 1.1 一句话形态

一个**完全离线、不登录、不联网**的 Android 原生训练记录工具，同时支持「按时长倒计时」与「按组计次」两种训练方式，两种方式共用同一套项目、历史与备份体系。依据：`README.md`「产品定位」段；`app/src/main/AndroidManifest.xml` 无 `INTERNET` 权限且 `allowBackup="false"`。

### 1.2 四个一级 Tab（实际落地）

底部导航为「时长 / 次数 / 历史 / 设置」四项。依据：

- `app/src/main/java/com/wanghoufan/zaijiuyidian/ui/AppRoot.kt`（`Tab.TIME` / `Tab.REPS` / `Tab.HISTORY` / `Tab.SETTINGS`）
- 真机证据 `docs/qa/evidence-v11/01-four-tabs-time.png`、`00-note12pro-final-four-tabs.png`
- 验收 `V11R2-AC01 PASS`（`docs/qa/产品验收追踪矩阵-P068-V1.1-R2.md` 第 14 行）

### 1.3 时长模式（TIME）

- 预设档位 + 自定义目标，范围 1–300 分钟；当前目标与预设重启后保留 → `AC-02 PASS`（V1.0 矩阵第 15 行，证据 `evidence/29-target-persisted.png`）
- 开始 / 暂停 / 继续 / 结束四态；**唯一主按钮**在开始与结束之间切换，暂停为次要按钮 → `TrainScreen.kt`
- 达标不自动结束，继续计时并显示「已超出」→ `AC-05 PASS`（V1.0 矩阵第 18 行，`evidence/31-over-target.png`）
- 结束需二次确认，可选择「计入历史 / 不计入」；不计入不产生记录 → `AC-04 PASS`（第 17 行）
- 提前结束保留当次目标快照（目标 25 分、实际 14 秒，记为 0.2/25，而不是 25/25）→ `AC-03 PASS`（第 16 行，`evidence/05-history-after-save.png`）
- 暂停期间不计入有效时长，记录标注「含暂停 N 次」→ `AC-06 PASS`（第 19 行，`evidence/52-pause-count-after-fix.png`）
- 锁屏/后台/设备重启不伪造成绩：重启后弹「计时被设备重启中断，最后可靠记录 00:10」→ `AC-07 PASS`（第 20 行，`evidence/47-before-reboot.png`、`48-reboot-recovered.png`）；实现依据 `TimerMath.kt` 的 `SystemClock.elapsedRealtime()` 单调时钟 + boot 判据

### 1.4 次数模式（REPS，V1.1 新增）

- 项目级计划：组数 × 每组次数（如 3×10、4×10）；改计划不回改历史，历史保存计划快照 → `V11R2-AC03 PASS`（V1.1-R2 矩阵第 16 行）
- 逐组录入：每组一个实际次数，可修改、可撤销、可超计划追加、可提前结束 → `V11R2-AC04 PASS`（第 17 行）；界面 `RepsScreen.kt`
- 草稿持久化：切 Tab / 锁屏 / 后台 / 进程被系统回收后可继续，草稿不计入历史 → `V11R2-AC05 PASS`（第 18 行，证据 `evidence-v11/03-reps-draft-28.png`）；实现依据 `Entities.kt` 的 `rep_draft` 单行表
- 总次数由每组 `rep_sets.actualReps` 求和，**不写秒数列**，避免单位混用 → `docs/architecture-facts.md`；`Entities.kt`
- 数据模型：`projects` / `sessions` / `active_session` / `rep_sets` / `rep_draft`；数据库 v2，显式 `MIGRATION_1_2`，无 destructive migration → `AppDatabase.kt`；`V11R2-AC10 PASS`（第 23 行）

### 1.5 历史与统计（三图 + 完整 CRUD）

- 三张图：成绩趋势（折线/柱）、每周训练频率（双轴，周一为周起点）、频率关系（散点 + 分组表）→ `ValueCharts.kt`、`Stats.kt`
- 时长模式看「分钟」，次数模式看「总次数 / 最佳单组」；「全部项目」只合并训练次数与活跃天数，绝不合并分钟与次数 → `V11R2-AC09 PASS`（第 22 行）
- 筛选（项目 / 全部 / 时间范围 / 搜索）、补录、编辑、软删、撤销、最近删除恢复、「排除含暂停记录」开关全部在 V1.1 实现 → `V11R2-AC07 PASS`（第 20 行）；`HistoryScreenV11.kt`
- 匿名复算样本被写进硬验收：周一 3×10=30、周三 4×10=40、周五 [12,10,10,8]=40、周日 5×10=50 → 周 160 次 / 4 次 Session / 单次最多 50 / 单组最佳 12 / 最多 5 组，`StatsTest` 断言通过 → `V11R2-AC08 PASS`（第 21 行）；样本原文见 `docs/plan/P068-Android-Dual-Mode-Training-V1.1-Approved-Plan.md`

### 1.6 备份与恢复（V3）

- 支持 JSON + CSV 导出；JSON 备份版本 V1 / V2 / V3 三档，V3 含项目模式、计次计划快照、每组 sets、计次草稿、上次选择等设置 → `BackupCodec.kt`（`APP_ID` 仍为 `duration-progress`，为兼容保留）；`V11R2-AC11 PASS`（第 24 行）

### 1.7 语音、字体、深色、权限

- 语音：本地 WAV + SoundPool，36 个 `res/raw/cue_*.wav`，约 3.2MB，可用 `tools/make_voice_cues.sh` 复现；有效训练期间每满 3 分钟播报一次，>99 分钟用通用播报；语音 / 提示音 / 震动三个开关互相独立 → `VoiceCues.kt`、`docs/architecture-facts.md`

- 权限：无网络权限、无存储大权限（走 SAF）、无需登录、无云服务 → `AndroidManifest.xml`

## 2. 完整使用旅程（安装 → 日常 → 换机恢复）

### 2.1 安装（用户视角 6 步，每步都有真实失败点）

1. 拿到 APK（`dist/P068-zai-jiu-yi-dian-v1.1.0-debug.apk`），小米/Redmi 机型先要打开「USB 安装」或「未知来源」，**这个开关在锁屏或重启后会自动关闭**，表现为 `INSTALL_FAILED_USER_RESTRICTED` → `agent.md` 踩坑第 2 条；`docs/risks.md` R4
2. 首次启动，进入「时长」页，默认浅色主题 → `evidence-v11/01-four-tabs-time.png`
3. 无引导页、无登录、无权限弹窗（除后续主动开自动备份）→ `AndroidManifest.xml`；`AC-18 PASS`
4. 首次看到底部四 Tab，其中「次数」「历史」「设置」为空态 → `AC-18 PASS`（V1.0 矩阵第 31 行、V1.1-R2 矩阵第 14 行）
5. 若用户此前装过 V1.0 / V1.0.1，`install -r` 覆盖安装后旧项目与旧记录仍在 → `V11R2-AC10 PASS`；`AC-R2-11 PASS`
6. 需要先做的一件事：设置页选一个备份目录（自动备份默认不开启，或已开但未授权目录）→ `SettingsScreen.kt`；`AC-R2-03` 依赖此步

### 2.2 日常使用（两种模式的两条主线）

**时长线**：选项目 → 选预设或自定义目标 → 点唯一主按钮开始 → 中途暂停/继续 → 到点后不自动结束，继续显示「已超出」→ 点结束 → 二次确认里选「计入历史」→ 历史页看到本次记录（目标快照 + 实际时长 + 含暂停次数）

证据：`AC-02`~`AC-08` 全部 PASS（V1.0 矩阵第 15–21 行）；截图 `evidence/01-train-light.png`、`02-running.png`、`03-paused.png`、`04-finish-sheet.png`、`05-history-after-save.png`

**计次线**：在「次数」页选项目 → 按计划组数逐组录入实际次数（stepper 或键盘输入）→ 完成一组 → 中途可切 Tab、锁屏、被系统回收，回来仍可继续（草稿）→ 可超计划追加、可提前结束 → 结束时给摘要 → 保存后计入历史

证据：`V11R2-AC03/04/05` PASS（V1.1-R2 矩阵第 16–18 行）；截图 `evidence-v11/02-reps-idle.png`、`03-reps-draft-28.png`

**统计线**：历史页切换项目/时间范围/搜索 → 切三张图 → 编辑某条记录 → KPI 与图表立即重算

证据：`AC-13 PASS`（V1.0 矩阵第 26 行）；`V11R2-AC06/07 PASS`（V1.1-R2 矩阵第 19、20 行）；截图 `evidence-v11/04`~`09`

### 2.3 备份与回滚（日常里最容易被忽略的一条）

- 数据变动后自动写一份 `zjyd-auto-*`，最多保留 7 个；恢复前自动写一份 `zjyd-safety-*`（不参与轮转）→ `AutoBackupManager.kt`

### 2.4 换机恢复（完整链路）

1. 旧机：设置 → 备份与恢复 → 导出完整备份（V3 JSON）→ 通过系统分享/文件管理器转出

3. 恢复内容：项目（含模式与计次计划）、全部会话（含目标快照、暂停统计）、每组明细、计次草稿、主题/字体/语音/震动/图表偏好/上次选择 → `BackupCodec.kt` V3 定义；`V11R2-AC11 PASS`

## 3. 后来才明确的需求（V1.0 没有、V1.1 才加，以及本该 Day 1 就问到的）

### 3.1 Day 1 原始规格的边界（必须先立这个基准）

`docs/plan/P068-Android-Development-Plan-V1.2.md`（源文件 `Duration_Progress_Android_SDD_V1.2.md`，2026-11-05）是本项目**唯一一次获批的 Day 1 规格**。它明确写了三件事：

1. **三个一级 Tab「训练 / 历史 / 设置」，顺序不可变**（V1.2 第 6 节）
2. **明确不做**：云服务、登录、Supabase、腾讯云、AI 教练、分享社区、排行榜、PWA、iOS、英文界面、**长期常驻后台服务**
3. 自动本地备份被定义为「**非阻塞增强**」，不是 V1.0 必备

也就是说：Day 1 的需求覆盖了「计时 + 历史 + 手动备份 + 浅深色 + 字体档位」，**完全没有计次模式、没有自动备份、没有锁屏语音、没有四 Tab**。

### 3.2 后来才明确的需求清单（按「出现时点」排序，每条给证据）

| N12 | **用户最终签收作为独立验收项** | `AC-20 OPEN`、`AC-R2-12 OPEN`、`V11R2-AC15 OPEN` | Day 1 把它写成 AC，但没有约定「谁在什么时候、用什么方式签收」，导致三个版本累积三张 OPEN |

### 3.3 这些遗漏的共同结构

**推断**（依据上述文件的时间顺序与内容差异）：Day 1 的提问方式是「你要做什么功能」，而不是「你训练时手机在哪、练完会不会看数据、换手机时数据怎么办、你还有没有别的训练类型」。前者得到的是功能清单，后者才能得到约束清单。本项目所有后期返工（N1→N2→N3→N7 是一条链，N4→N5 是一条链）都源自约束缺失，而非功能没想全。

证据支撑这条推断的关键点：`P068-Android-Dual-Mode-Training-V1.1-Approved-Plan.md` 第 31 行写「不新增第 4 个底部 Tab」，而下一版 `P068-Android-Dual-Mode-Training-V1.1-R2-Final-Approved-Plan.md` 第 9 行写「最终明确底部四 Tab」——**同一个产品在两版获批计划之间自我推翻**，这是约束缺失最直接的可定位证据。

## 4. 关键 UI / 操作模式（以及哪些推翻了最初设计）

### 4.1 四 Tab 结构与信息分工

| Tab | 承担什么 | 不承担什么 | 证据 |
|---|---|---|---|
| 时长 | 计时训练主战场：目标、开始/暂停/结束、超时提示、结束确认、语音与震动开关的即时可见状态 | 不承载计次录入 | `TrainScreen.kt`；`evidence-v11/01-four-tabs-time.png` |
| 次数 | 计次训练主战场：计划、逐组录入、修改/撤销、超计划追加、提前结束、草稿恢复 | 不复用时长页的计时组件 | `RepsScreen.kt`；`evidence-v11/02-reps-idle.png`、`03-reps-draft-28.png` |
| 历史 | 两种模式共用的记录库 + 三图 + 筛选 + 补录/编辑/软删/撤销/最近删除恢复 | 不按模式拆成两个历史页 | `HistoryScreenV11.kt`；`evidence-v11/04`~`09` |
| 设置 | 项目管理、训练偏好、外观（字体/深色）、备份与恢复（含自动备份） | 不承载训练操作 | `SettingsScreen.kt`；`evidence/07-settings.png`、`08-settings-data.png` |

### 4.2 唯一主按钮原则

时长页只有**一个**视觉主按钮，在「开始训练」与「结束训练」之间切换；暂停/继续是次要按钮，不计入主操作序列。依据：`TrainScreen.kt`；`evidence/01-train-light.png`、`02-running.png`。

这条原则的价值在于：训练场景用户常常单手、出汗、注意力分散，两个同等权重的按钮会导致误触结束。它在 V1.0 就成立并一直保留（V1.0 矩阵 AC-04 验证「不计入」路径）。

### 4.3 计次逐组输入（这是本项目最特殊的一种交互）

- 每组一个 stepper + 可直接键盘输入数字；不追求「一次填总次数」
- 每完成一组立刻固化，可修改、可撤销；已完成的组不可被后续计划变更回写
- 允许超计划追加（计划 3 组，实际做 4 组仍可保存）→ `V11R2-AC04 PASS`
- 允许提前结束并给摘要（计划 4 组，做了 2 组=20 次仍可保存）→ 同上
- 离开页面不丢：草稿落 `rep_draft` 单行表，回来提示「去继续次数草稿」→ `V11R2-AC05 PASS`；`Entities.kt`

**推断**（依据 `RepsScreen.kt` 存在 stepper 与键盘双通道、以及 `agent.md` 第 14 条「改计划后下一组建议值不更新（remember key 缺 nextReps）」）：这套交互在实现期至少经历一次「建议值不刷新」的真实缺陷，说明「下一组默认值」是产品语义的一部分，而不是 UI 细节。

### 4.4 历史图表切换模式

- 三张图用同一区域切换，不并列堆叠，避免小屏一屏塞三张图
- 图表与记录列表在同一页，改一条记录后 KPI、图、分组表同时重算 → `AC-13 PASS`（V1.0 矩阵第 26 行）
- 「全部项目」有明确警告语义，不混单位 → `V11R2-AC09 PASS`；`evidence/16-all-projects-warning.png`
- 「排除含暂停记录」是一个可见开关，不是隐藏过滤 → `evidence/15-scatter-exclude-paused.png`；`V11R2-AC07 PASS`

### 4.5 设置页分组模式

四个分组：项目管理 / 训练偏好 / 外观 / 备份与恢复。依据：`SettingsScreen.kt`；`AC-18 PASS` 明确「设置页只有训练偏好/外观/数据管理/关于，无登录、无云端入口」（V1.0 矩阵第 31 行）。

备份与恢复被放进设置页而不是独立 Tab，这一决策使底部 Tab 得以保留四个而不是五个。**推断**：这是 R2 明确「历史与设置共用」后的自然结果（`P068-Android-Dual-Mode-Training-V1.1-R2-Final-Approved-Plan.md` 第 9 行「历史与设置共用」）。

### 4.6 被推翻的最初设计（硬证据）

**推翻项：三 Tab → 四 Tab。**

- 原设计（Day 1 原规格，2026-11-05）：`docs/plan/P068-Android-Development-Plan-V1.2.md` 第 6 节——三个一级 Tab「训练 / 历史 / 设置」，顺序不可变
- 第一次加固（V1.1 首版获批计划）：`docs/plan/P068-Android-Dual-Mode-Training-V1.1-Approved-Plan.md` 第 17 行仍写「三 Tab」，第 31 行更明确写「**不新增第 4 个底部 Tab**，不把同一个功能复制成多个卡片……TIME 与 REPS 的功能由所选项目驱动」
- 最终推翻（V1.1-R2 终版获批计划）：`docs/plan/P068-Android-Dual-Mode-Training-V1.1-R2-Final-Approved-Plan.md` 第 9 行——「用户反馈双模式必须在**同一个 APP**内呈现独立训练入口，最终明确 **底部四 Tab：时长 / 次数 / 历史 / 设置**，历史与设置共用」
- 落地验证：`AppRoot.kt` 四 Tab；`V11R2-AC01 PASS`；对照截图 `evidence-v11/00-note12pro-final-four-tabs.png`

**为什么会被推翻（推断，有行为证据）**：旧方案的「由所选项目驱动模式」假设用户只有一个项目、或项目模式切换很自然；真实使用中用户会同时练计时项目和计次项目，同一 Tab 内按项目切换会导致「我在哪个模式」持续困惑，且计次草稿与计时进行态会在同一页争抢主按钮。用户的真实反馈是「必须在同一个 APP 内呈现独立训练入口」，这句话本身就是对「只用项目驱动」的否定。

**未推翻但被加固的设计（对照证据）**：

- 唯一主按钮 → 保留，V1.1 未改（`TrainScreen.kt` 仅 +19 行）
- 达标不自动结束 → 保留（`AC-05 PASS`）
- 结束不改暂停计数 → 保留（`agent.md` 第 3 条修复后固化）
- 浅色默认 + 深色可切 → 保留，但未加 SYSTEM（见 1.9）
- 应用内字体档位 → 保留并成为 V1.1 AC-13 的一部分

## 6. 验收方法（普通用户 vs 开发者；真机、多机型、备份恢复、锁屏语音）

### 6.1 两种验收者的分工必须分开

| 角色 | 验什么 | 本项目实际证据 |
|---|---|---|
| 普通用户（代码所有者本人） | 手感与语义：按钮好不好按、数字看不看得清、结束后能不能确认、历史能不能看懂、恢复后数据对不对 | `AC-20`、`AC-R2-12`、`V11R2-AC15` 三个「用户签收」项**全部 OPEN**，说明这套分工在实际执行中最先被跳过 |
| 开发者 / 智能体 | 可判定项：单测、真机截图、元数据回读、独立复算、哈希核对、迁移验证 | 32/32 单测；三份追踪矩阵中 AC-01~AC-19 有 30 余条可判定证据 |

**关键结论**：本项目 30 余条技术验收 PASS，但 3 个用户签收项 OPEN。这不是「验收没做」，而是「验收做了但没闭环」。任何复盘如果只说「测试全绿」，都掩盖了这个事实。

### 6.2 真机验收的四类手段（按证据强度排序）

1. **元数据回读**（最强）：不只看截图，而是拉库或读备份 JSON 核对 `actualSec` / `pauseCount` / `pausedSec` / `targetSec` / 每组 `actualReps`。实例：`evidence-r2/backup-files-and-metadata.txt` 记录 25:53 训练 → `actualSec=1553, pauseCount=1, pausedSec=30, targetSec=1500`（`AC-R2-06`）
2. **独立复算**：用 Python 在设备外重算一遍，与界面数字逐项对齐。实例：V1.0 `AC-10/11/12` 三条均为「真机 + 独立复算」；V1.1 `V11R2-AC08` 用 `StatsTest` 手算断言
3. **截图取证**：`docs/qa/evidence/` 41 项、`evidence-r2/` 11 图 + 6 文本、`evidence-v11/` 17 项；文件名即场景（如 `15-scatter-exclude-paused.png`）
4. **包哈希核对**：`adb` 安装后回读 `base.apk` 的 SHA-256，与 dist 比对。实例：三台设备哈希一致（`docs/handoff/HANDOFF.md`、`evidence-v11/push-2026-11-06-v1.1.0.txt`）；V1.0.1 的 Debug 证书 SHA-256 `8e82a797…11cf3`（`AC-R2-11`）

### 6.3 多机型验收：必须按「版本 × 能力」排矩阵，不能按机型数量算

实际覆盖（`docs/qa/evidence-r2/device-matrix.txt`、V1.1-R2 矩阵第 27 行）：

| 设备 | Android | 实际完成 | 未完成 |
|---|---|---|---|

### 6.4 备份恢复验收（最容易被「看起来成功」骗过的一项）

必须验的五件事，缺一不可：

1. 文件真实落盘且在 APP 私有目录之外（`AC-R2-03`：`/sdcard/P068Backup/`）
2. 内容完整（V3 含 2 项目 / 4 记录 / 3 条计次 / 9 组明细 → `V11R2-AC11`）
3. 恢复后 KPI **立即正确**，不需要重启（`evidence-v11/10-restore-v3-immediate.png`；这是 `agent.md` 第 13 条踩坑的回归项）
4. 恢复前有保护点、可再回滚（`AC-R2-05`：从 28 条版本恢复到 1 条，再从保护点回到 28 条）
5. 损坏文件被拒、重复导入新增 0（`AC-15`：`evidence/26-corrupted-rejected.png`、`44-duplicate-merged.png`）

**证据缺口**：失败路径（目录授权被撤、空间不足、写入异常）从未实测，只在 `AC-R2-08` 验了「通知权限被撤」这一种降级。这是本项目验收体系里最大的一块空白（`docs/risks.md` R5）。

### 6.5 锁屏语音验收（必须看服务日志，不能看界面）

- 判据：锁屏期间服务侧日志出现 `voicePlayed=true`，且前台 UI 同时刻为 `voicePlayed=false`（不重复播报）→ `AC-R2-07`
- 实际节点：9/12/15/18/21/24 分钟与目标节点全部命中 → `docs/qa/evidence-r2/voice-cues-observed.txt`
- **必须注意的证据失效**：`adb logcat` 环形缓冲区会被后续重装清空，原始日志已丢失，现存为抄录（`docs/risks.md` R9 记录了 25:53 会话的保留情况）。正确做法是流式写入文件，不用 `adb logcat -d`

### 6.6 一条可复用的验收流程（本项目实际走通的）

1. 构建 → 记录 versionCode / versionName / 字节数 / SHA-256（`dist/SHA256SUMS.txt`）
2. 单测全绿（32/32）
3. 逐台 `adb -s <serial> install -r` → 回读 base.apk 哈希 → `am start -n` 拉起 → 截图确认前台是目标应用
4. 按 AC 矩阵逐条跑，每条产出一张图或一份文本
5. 有争议的数字做独立复算
6. 拉库/读备份元数据核对
7. 写 `docs/qa/QA-REPORT-*.md` + `产品验收追踪矩阵-*.md`，PASS / PARTIAL / OPEN 三态如实标注
8. 用户签收（本项目始终缺这一步）

## 8. 可直接复制给云端计划者的 Day 1 提示词

> 以下整段可直接复制。全部为普通用户口吻，不出现数据库、框架、接口名称。

```text
我要做一个安卓手机上的训练记录小工具，名字先叫《再久一点》。

先说清楚：这个软件必须完全离线。不注册、不登录、不连网、不上传、不弹广告、不要任何账号体系。断网、开飞行模式都要能从头用到尾。

【我的训练有两种，必须都支持】
第一种是计时训练：比如跑步、静蹲、平板支撑，我设一个目标时长，点开始倒计时。
第二种是按组计次：比如俯卧撑、深蹲、哑铃，我定好"做几组、每组几个"，然后一组一组地记实际做了多少个。

这两种训练我要在同一个软件里用，但入口必须分开，我不想在一个页面里靠切换项目来区分自己到底在哪种模式。所以底部要有四个入口，从左到右固定是：
1）时长
2）次数
3）历史
4）设置
这四个顺序不能变，不要藏在菜单里，不要合并。

【计时训练要怎么做】
- 有常用档位（比如 15、20、25 分钟），也能自己填分钟数，范围大概 1 到 300 分钟。
- 一个页面只有一个主按钮，没开始时是"开始训练"，开始了就变成"结束训练"。暂停和继续是旁边的小按钮，不要和主按钮一样大，我训练时手是湿的，容易点错。
- 到达目标时间后不要自动结束、不要自动保存。我经常想多做一会儿，所以到点后继续计时，同时显示"已超出多少"。
- 点结束要给一个确认，让我选"计入历史"还是"不计入"。选不计入就真的不留记录；如果我只是手滑关了确认框，计时不能被偷偷清掉。
- 中途暂停的时间不算进实际时长，但要在记录里标出来"这次含暂停几次"，别让我自己猜。
- 历史里每条记录的"目标"要是当次的目标，不是我现在的目标。我以后改了目标，旧记录不能被改。
- 手机锁屏、切到别的应用、甚至中途重启，都不能凭空多出成绩。如果是真的重启了，就老实告诉我"计时被中断，最后可靠的记录是多少"，让我决定保不保存。

【按组计次要怎么做】
- 我先给一个项目定计划，比如 3 组、每组 10 个。
- 训练时一组一组记：做完一组就填这一组实际做了几个，数字要么点加减，要么直接打字输入，两种都要有。
- 填错了能改，也能撤销刚填的那一组。
- 偶尔我状态好多做一组，或者状态差做两组就停，这两种都要能保存，不要卡死我说"必须做满"。
- 最关键的：如果我在记录过程中切到别的页面、锁屏、或者手机把软件清掉了，回来必须能接着记，已经填的组不能丢。没保存完的这部分不能算进历史。

【历史与统计怎么做】
- 两种训练共用同一个历史页，不要拆成两个历史页。
- 我要能看到三类图：
  1）每次成绩的趋势（按时间看我是进步还是退步）
  2）每周练了几次（一周从周一开始算，没练的那周要留空，不要画成 0）
  3）"练几次"和"平均成绩"之间的关系（每周一个点，旁边配一张按次数分组的表，能让我自己核对）
- 计时看分钟，计次看总次数和单组最好成绩。千万不要把分钟和次数加在一起算，那是两种东西。
- 如果切到"全部项目"，只能合并"练了几次、练了几天"，不能合并成绩。
- 历史记录要能补录、能编辑、能删、删错了能撤销、能找回最近删除的。
- 我改一条记录以后，上面的数字和图必须马上跟着变，不能等我重启软件才更新。
- 图上要能按项目筛、按时间段筛（最近 10 次、30 次、全部）、能搜索备注。

【设置里要有什么】
- 管项目：新建、改名、切换、归档、恢复。至少要留一个项目在用。
- 训练偏好：语音提示开不开、提示音开不开、震动开不开，这三个要独立开关。
- 外观：浅色/深色，默认浅色。另外我要能在软件里单独调字号，至少四档（小、标准、大、特大），默认标准。调到最大时按钮和文字不许重叠、不许挡住主按钮。
- 备份和恢复。

【备份是我最看重的一条】
- 我要能一键导出完整备份文件，也要能导出一份表格（Excel 能打开），表格是中文表头。
- 备份文件要包含：所有项目、所有训练记录、每一条计次训练里每一组做了几个、以及我的所有设置。
- 我要能自动备份：我指定一个手机文件夹，之后每次数据有变化就自动存一份，最多保留最近 7 份，旧的自动删掉。手动导出的文件和"恢复前的保护文件"不许被自动删。
- 恢复前必须自动存一份"恢复前的样子"，我恢复错了能退回去。
- 导入的时候要能预览：这个文件里有几个项目、几条记录、什么时候导出的。
- 导入要能选"合并"还是"覆盖"。同一个文件重复导入不能变成两份数据。
- 文件坏了要直接告诉我文件有问题，不能悄悄把现有数据搞乱。
- 我换手机的时候，就是这个流程：旧手机导出文件 → 新手机装同一个软件 → 导入 → 数据全回来。

【语音提醒】
- 训练中途每满 3 分钟给我报一次时间，让我不用看屏幕。
- 手机锁屏、放口袋里也要能提醒。（我知道系统可能延迟，但我需要"大部分时候能响"，不能只在屏幕亮着才响。）
- 语音不要用系统自带的那个机器音，我要自己可控的声音。
- 语音、提示音、震动三个开关分开，不要绑在一起。
- 通知栏不要露出我在练什么、练了多久这类私人信息。

【界面上的基本要求】
- 全中文，不要出现"测试""演示数据""开发中"这种字。
- 不要有登录入口、不要有云端入口、不要有分享社区、不要排行榜。
- 数字要大、对比度要够，我在健身房光线差、手在抖的时候也要能看清、按准。
- 空状态要告诉我下一步该点哪里，不要空白一片。

【验收方式，这个必须提前说定】
- 不许只跑测试就说做完了。必须在真手机上，装上去，用一遍。
- 至少要在两台不同安卓版本的手机上装一遍（我手上是小米/红米），确认都能装、都能用。
- 备份恢复必须真做一遍：导出 → 卸载 → 重装 → 导入 → 核对记录数量、每组数字、统计图都对。
- 锁屏语音必须真锁屏测，至少测到 3 分钟和 6 分钟两个点，并且要能拿出证据（日志或录屏），不能只看界面说有。
- 长时间训练要真练一次 15 到 25 分钟的，不能只测 30 秒。
- 给我交付的时候要说清楚：安装包文件名、版本号、文件大小、以及这是不是正式签名（能不能长期用、能不能上架）。
- 最后一条：必须我自己亲手用一遍、亲手做一次备份恢复，我说"可以"才算验收通过。你跑通测试不算。

【明确不要做的】
- 不要云服务、不要登录、不要联网、不要上传我的数据。
- 不要网页版、不要苹果版、不要英文界面。
- 不要 AI 教练、不要社区、不要排行榜。
- 不要为了做功能牺牲数据安全：升级软件不能清空我已有的记录。

【如果只能先做一版】
先做"计时训练 + 历史 + 手动备份 + 浅色深色 + 字号"这一版，但要按上面的结构留好位置，不要写死成"只有一种训练"，以后加按组计次的时候不能推倒重来。
```

### 9.6 这些迭代的共同性质（结论）

把这 18 条分成两类看：

- **可提前预防的（I1、I2、I3、I5、I8、I9、I12、I18）**：共 8 条。它们的共同点是「有明确的反例可以写进 Day 1 的验收清单」。例如「结束动作不得改变暂停计数」「恢复后 KPI 必须立即正确，不需重启」「改计划后下一组建议值必须跟着变」——这三条完全可以作为「验收判据」写进 Day 1 提示词的第 8 节，而不需要懂技术。
- **不可提前预防的（I4、I6、I7、I10、I11、I13、I14、I15、I16、I17）**：共 10 条。它们依赖具体的库行为、厂商 ROM、并发时序、测试工具能力。Day 1 说全了也照样会遇到，只能靠「遇到就记进踩坑表、并把判据升级成回归项」来消化。

**这是本报告最重要的一条结论**：Day 1 提示词的价值不在于消灭全部迭代，而在于把「可预防的 8 条」变成验收判据，从而把迭代从「返工」降级为「回归」。本项目实际做对了一部分——`agent.md` 16 条踩坑 + `经验一句话.md` 已在做这件事；但因为没有在 Day 1 就写进验收判据，所以这些坑是「踩了之后才记录」，而不是「记录之后不再踩」。

### 9.7 一个可操作的分界

给云端计划者的 Day 1 提示词，第 8 节「验收方式」里再补三句，就能覆盖 9.6 里 8 条可预防项中的 5 条：

1. 「结束训练这个动作，本身不能改变"暂停过几次"这个数字。」
2. 「恢复备份以后，所有统计数字必须马上是对的，不能等我重启。」
3. 「我改了训练计划，下一组默认建议的数字要立刻跟着变，不能还显示旧计划。」
4. 「软件升级/覆盖安装以后，我原来的记录一条都不能少。」
5. 「装完之后要能核对：手机上装的这个包，和你给我的那个包是同一个。」

这五句都是普通用户能说出口的话，但每一条都对应过一个真实 P0 缺陷。
