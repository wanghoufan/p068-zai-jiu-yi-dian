## 1. 项目最初目标、当前已核实状态、历史覆盖度与证据缺口

**最初目标**：一个只给本人、完全离线的 Android 训练记录工具，覆盖「练多久」（倒计时）与「练多少组多少次」（计次）两类训练，共用一份历史与一套备份。

**当前已核实状态**：1.1.0 debug APK 已产出并装到 3 台 Redmi（Android 11 / 14 / 15）；四 Tab（时长 / 次数 / 历史 / 设置）已实现；Room v2 迁移、备份 V3、自动备份、锁屏语音前台服务均已落地并有代码与截图证据。**但项目仍未「完成」**：三份验收矩阵各留一张用户签收 OPEN，至今没有一次可引用的「用户已确认可用」时刻。

**历史覆盖度**：Git 仅 2 天 6 个提交，但文档覆盖完整——4 份获批计划、2 份 HTML 交互原型、3 份 QA 报告、3 份验收追踪矩阵、96 个证据文件。需求的**真实口头来源**（用户原话、何时提出计次）不在仓库内。

**证据缺口**：
1. 用户提出「计次」「锁屏语音」「自动备份」的原始对话未留存，所有「谁先提出」均为推断。
2. V1.0 计划（V1.2）与 V1.1 两版批准之间的用户反馈语境只有计划文件转述。
3. 三台真机的系统小版本号仅在 `device-matrix.txt` 有记录，未逐台回读设置页。

## 3. 可预防返工 Top 5（按影响排序，不虚构工时）

**L1｜计次模式缺席导致「四层同改」**
- 现象：V1.2 宪法定义为「通用时长进阶工具」，全篇无「组/次数」概念；一天内两版获批计划互相否定。
- 影响：导航（3→4 Tab）、数据（`sessions` 只有秒数字段 → 新增 `rep_sets`/`rep_draft` + `mode`）、备份（V1→V3）、统计（双口径）四层同时动，`693f685` 单提交 46 文件。
- 可预防性：**高**。用户画像已写「可能在健身/专注练习中」（`V1.2:76`），任何有经验的计划者第一组问题就会问「计时类还是计次类，还是两者都有」。
- 一句话补救：Day 1 问「除了掐表，引体向上这种要不要一组一组记？要不要单独的入口？」

**L2｜锁屏/后台语音从未进验收条款，导致整轮前台服务补课**
- 现象：画像写「能锁屏」，计划把锁屏播报降级为「先验证」，AC 全表无一条要求锁屏播报；V1.0 QA 自认「能力缺口」。
- 影响：V1.0.1-R2 整版转向 `specialUse` 前台服务 + 常驻通知 + `PARTIAL_WAKE_LOCK`，36 个 WAV 资产与生成脚本，三台机器重验。
- 可预防性：**高**。「练的时候人在哪、手机在哪」是一个普通用户能直接回答的问题。
- 一句话补救：「我练的时候手机放地上、屏幕是黑的，锁屏了也得提醒我。」

**L3｜两类「闭环项」没有 owner 与时点，条款写了也不执行**
- 现象一（用户签收）：`V1.2:239` AC-20 明文「用户亲自走通一次并明确签收」，但三版各留一张 OPEN（`产品验收追踪矩阵-P068-V1.0.md:33`、`-V1.0.1-R2.md:24`、`-V1.1-R2.md:28`），`docs/risks.md:6` R1 长期挂账。
- 现象二（文档回写）：`docs/architecture-facts.md:56` 的设备状态与 `HANDOFF.md:39`、`-V1.1-R2.md:27` 互相冲突，且 R2 计划 `:22` 早已警告过同类滞后。
- 影响：不产生代码返工，但**项目至今没有「可用」的裁定依据**；文档漂移会让下一次接手按错状态开工。
- 可预防性：**高，且成本最低**。30 余条技术断言全部有人跑，唯独「必须本人做」那一环没人安排。
- 一句话补救：「做完不算完，安排哪天我自己练一次、做一次备份恢复，我说可以才算数。」

**L4｜备份格式与数据模型无对账制度，V1→V2→V3 三次扩展**
- 现象：V1.2:159 只写 `schemaVersion`「支持以后迁移」，:165 备份清单不含偏好；R2 计划 `:18` 自己核实「当前完整备份没有全部用户设置」→ V2 补偏好；计次上线 → V3 补组明细；`docs/risks.md:47` R11：V1/V2 备份恢复不出计次数据。
- 影响：`BackupCodec.kt` 三轮扩展（V3 +297/−23）、V3 恢复 KPI 变 0 的 P0（`agent.md:31`）、R11 成为长期用户可见隐患。
- 可预防性：**中高**。不需要预知计次，只需要一条「Room 实体清单 = 备份字段清单」的建表当期对账。
- 一句话补救：「换手机导备份，昨天每组做几个要一条不差回来。」

**L5｜反馈节奏进入验收现场才补（F-01/F-02）**
- 现象：V1.2 设置页只有提示音/震动，无「开始要有反应」「每 3 分钟报时」；验收现场用户追加，矩阵标注「非原计划 AC」（`产品验收追踪矩阵-P068-V1.0.md:43,47,48`）。
- 影响：36 个语音资产后补、TTS→WAV 选型试错（`agent.md:23`）、播报逻辑后来搬进前台服务。
- 可预防性：**中**（节奏可预防；具体音色/资产属正常迭代）。
- 一句话补救：「点开始要有反应，每满 3 分钟报一下。」

## 4. 正常演化 / 新出现的产品认识（不应追责的部分）

1. **计次需求本身的浮现**（不是错，错在没问）。
2. **MIUI「USB 安装」锁屏即关**（`agent.md:20`）、**SAF 目录名被输入法打乱**（`:27`）、**真机无 sqlite3**（`:33`）、**其他应用抢占前台**（`:34`）、**Gradle 缓存损坏**（`:24`）：平台与 OEM 行为不可预知。
3. **字体默认值手感**（115% 不是 100%）：偏好类参数只能靠真机反馈收敛。
4. **自动备份优先级后移**：技术分级合理，只是没把优先级选项抛给用户。
5. **系统 TTS 引擎与中文包因机型而异**：这是真实平台约束；可预防的是绕开它的选型，不是约束的存在。

## 6. UI / 布局 / 导航 / 页面密度 / 高频操作的可复用经验

1. **一级入口数量是可验收的硬指标**，不是审美。两种练法平级 → 四个 Tab；「模式开关」方案应被明确禁止（`V1.1-R2:49`）。
2. **两套单位同屏防错**：时长「分:秒」、次数「组×次」；历史卡片必须带单位标签；「全部项目」视图只放共同口径（次数/天数），单项目视图才放该项目口径（`V1.1-R2:56–57`）。
3. **训练态要能单手盲操**：「完成本组」必须是页面最大最好按的控件；`NextSetCard` 的 `remember` key 缺 `nextReps` 导致改计划后建议值不更新（`agent.md:32`）——高频控件的状态派生必须显式列出输入源。
4. **反馈多通道且即时**：开始一声、每组一声、达标一声；锁屏时唯一通道是声音+震动，所以它们不是装饰。
5. **破坏性操作双保险**：短撤销（实测 2.7s → 改为 4.2s）+ 长期「最近删除」。证据链：`evidence/22-delete-undo-toast.png`、`23-undo-restored.png`、`24-recent-deleted-restore.png`。
6. **重操作要有可见过程**：Mutex 不可重入导致恢复永不返回（`agent.md:25`），用户侧表现就是「点了没反应」；恢复期间必须有进度/禁用态与结果回执。
7. **字体与主题属并行设置**，切换不得丢业务状态（AC-17，`V1.2:236`）。

## 7. 外部条件 / 测试资源 / 授权 / 正式部署的可提前准备项

1. **设备清单是 Day 1 交付项**：几台、型号、Android 大版本、屏幕尺寸、谁提供、每台「USB 安装」开关状态。本项目最终 3 台（Android 11/14/15），计划期只登记 1 台且注明「ADB 授权未核实」（`V1.2:203`）。
2. **每台到机先跑 5 分钟环境探针**：USB 安装开关、SAF 选择器、通知权限、省电策略。MIUI 机型保持亮屏重开开关再装，避免把环境问题误判为 APK 缺陷。
3. **备份落点必须是用户可长期持有的 SAF 目录**，不能是 App 私有目录（卸载后仍可恢复，`V1.0.1-R2:64`）。
4. **旧版基线**：一台装过 v1 的真机 + 一份 v1 备份样本，否则迁移永远验不了。
5. **语音资产必须可重建**：36 个 WAV 由 `tools/make_voice_cues.sh` 生成，不靠二进制沿用。
6. **构建环境**：JDK 17、Gradle 8.14.3、AGP 8.13.0、compileSdk 36。
7. **正式分发前置**：当前为 DEBUG 测试签名；上架或长期安装需 release 签名与 versionCode 递增策略。

## 9. 适用范围、反例与「不能推广为通用规则」的部分

- **可推广**：双模式入口 = 两个平级一级入口；备份字段与实体清单对账；闭环项要有 owner 与时点；以哈希认包、逐台记录 PASS/FAIL/NOT_RUN。
- **不可推广为硬规则**：
  - 「48 小时内交付三个版本」在本项目成立（个人使用、单一用户、无发布压力），但对有多方干系人的项目**不成立**——它正是本项目质量问题（三张 OPEN、文档漂移）的直接诱因。
  - 「四 Tab」不是通用结论：单模式工具三个 Tab 更合理。真正可推广的是「入口数量由用户的使用分流决定，且须拍板」。
  - 「36 个本地 WAV」不是通用方案：小体量提示音可用系统能力；只有当平台 TTS 不可控且需要锁屏播放时才值得做资产化。
- **反例（A 提出、本报告确认成立）**：撤销时长「≥4 秒」、「最近删除」入口、「字体 115% 默认」这类**具体数值**不能靠 Day 1 追问得出，只能靠验收兜住；要求计划者在 Day 1 精确写出这些数字是不合理预期。

## 10. 用户 / 计划者 / 开发者责任划分与下一次做法

| 差距 | 用户合理应表达 | 计划者应主动发现 | 开发者负责解决 | 下次做法 |
|---|---|---|---|---|
| L1 计次与四 Tab | 是（练什么只有他知道） | **是（画像已给线索）** | 数据层/迁移/备份实现 | Day 1 问第 1 问；计划里把「入口数量」列为待拍板项 |
| L2 锁屏语音 | 部分（一句话） | **主责（画像→AC 翻译）** | `specialUse` 选型、权限降级 | Day 1 问第 2 问；每个使用场景追问「锁屏后呢」 |
| L3 签收/文档闭环 | 部分（可主动声明） | **主责（缺安排机制）** | 无法代做 | Day 1 问第 10 问；验收矩阵最后一行写日期与证据形态；每轮收工回写 facts/risks |
| L4 备份三级扩展 | 否 | **主责（对账制度）** | V3 回填缺陷 | 建表当期对账；备份第一版带升级规则与旧文件提示话术 |
| L5 反馈节奏 | 部分 | **主责（核心体验未进 AC）** | 资产制作与实现 | Day 1 问第 3 问；写反馈节奏表进 AC |
| 主题三态/字号下限 | 部分（全局规则自定，批准时未对照） | 部分（审批时应提示冲突） | 实现（若补做） | 计划审批时逐条对照用户既有偏好清单 |

**总体裁定**：本项目最大两笔返工（L1、L2）**不能归给「用户没说」**——画像里已经给了「健身」「锁屏」两条线索，缺的是计划者把它们翻译成需求提问与 AC 条款这一动作。唯一「条款已写、纯因流程未执行」的是 L3 签收缺口，责任最清晰。
