## 1. P0 只读预检结论（2026-11-10 实测）

| 项 | 事实 | 对同步的影响 |
|---|---|---|
| 网络权限 | 预检时 `AndroidManifest.xml` 无 `INTERNET`（现已声明，见 §11.3 注 5），产品当前宣称「不联网不登录不上传」 | 接入必须新增权限，并改写 README/隐私口径为「默认仅本机，云同步由用户主动开启」 |
| 数据库 | Room `version = 2`，`AppDatabase.kt`；导出 schema `app/schemas/2.json` | 需新增 `MIGRATION_2_3`，只加列不加表也可行；不得用 destructive |
| 主键 | `projects.id` / `sessions.id` / `rep_sets.id` 均为 `UUID.randomUUID().toString()` | 跨设备天然唯一，可直接作 `record_id` |
| 时间戳 | 各表有 `createdAt` / `updatedAt`（epoch millis，设备本地时钟） | 不能直接当同步游标；需服务端 `server_updated_at` 或单调 revision |
| 软删 | `sessions.deletedAt` 有软删；`projects` 是硬删 `DELETE FROM projects`；`rep_sets` 无软删、改一组按 `(sessionId, ordinal)` 覆盖 | 同步必须补墓碑：`projects`、`rep_sets` 需增加删除标记或改为写墓碑表 |
| 子表版本 | `rep_sets` 只有 `actualReps`，无 `updatedAt` | 组级改动无法增量判断，需给父 Session 加 revision 或给 rep_sets 加 `updatedAt` |
| 本机态表 | `rep_draft`、`active_session` 是单例设备本地工作状态 | **不同步**；否则两机会互相覆盖正在进行的训练 |
| 备份 | `BackupCodec` V3 含 mode / plannedSets / targetRepsPerSet / sets / draft，带 checksum，兼容 V1/V2 | 云端同步不替代它；备份格式不因 V1.2 改动 |
| ID 稳定 | 已完成 V1/V2→V3 兼容与导入合并 | 首次上云可复用备份数据做「首传预览」 |

结论：数据模型改造量可控，主要缺口是 **projects/rep_sets 的墓碑** 与 **同步游标**，不是重写数据层。

## 2. 目标与非目标

目标（V1.2）：
1. 用户在「设置 → 云同步」主动登录并开启后，四 Tab 数据在本人多台设备间按记录增量同步。
2. 离线优先：无网/云端失败时训练照常，改动进 Outbox，恢复后按幂等规则补传。
3. 权限最小化：只能读到自己 `owner_uid` 的记录；未登录、过期 token、伪造归属一律拒绝。

非目标：
- 不做多人共享、排行榜、社交。
- 不做云端快照备份（后置 V1.3）；不做 Web 端。
- 不改四 Tab 训练交互，不把同步入口放进训练流程。

## 3. 数据模型（草案）

新增同步元数据（建议加列，不改主键）：

| 表 | 新增列 | 说明 |
|---|---|---|
| `projects` | `revision INTEGER NOT NULL DEFAULT 1`、`deletedAt INTEGER` | 把硬删改为软删 + 墓碑；归档 `archivedAt` 与删除语义分开 |
| `sessions` | `revision INTEGER NOT NULL DEFAULT 1` | 保留现有 `deletedAt` |

- `project_slug` 固定 `p068_duration_tracker`；云端每表带 `owner_uid`。
- 不同步：`rep_draft`、`active_session`、外观/语音等本机偏好。

## 4. 同步协议

1. 写路径：本机事务内写业务表 + `sync_outbox`，UI 只报「已保存到本机」。
2. 上行：按 `mutationId` 幂等提交；更新携带 `baseRevision`，云端影响 0 行＝冲突，不静默覆盖。
3. 下行：按 `(server_updated_at, id)` 游标拉增量；写入前校验 `revision`，本地有未确认改动时先标记冲突。
4. 冲突：训练记录是追加型，冲突面小。策略＝保留两版（本地 + 云端副本），在「云同步」页列一条「待处理」，默认不自动合并。
5. 删除：墓碑同步，保留 90 天后清理；离线超 30 天的设备恢复时全量重算统计，不累加两端合计。
6. 触发：进前台、写入后（去抖）、手动「立即同步」。不做常驻轮询。
7. 状态暴露：`仅本机` / `待同步 n` / `同步中` / `已同步` / `冲突 n` / `同步失败(原因)`，均在设置页，不打扰训练。

## 5. 认证与权限

- 登录：**用户名 + 密码**（CloudBase 身份认证）；不做匿名登录作主路径。草案原定邮箱验证码，定稿改为用户名+密码（见 §12-4）。
- 客户端只允许 Publishable Key + 用户 Access Token；`service_role`、管理员 API Key、数据库连接串一律不进 APK。
- PG 侧：每业务表 `ENABLE ROW LEVEL SECURITY`，`SELECT/INSERT/UPDATE/DELETE` 均限 `owner_uid = auth.uid()`；`UPDATE` 同时校验旧行与新行；`anon` 不授予任何私有表权限。
- 跨 APP 隔离不假设天然成立：本环境当前仅 P068 一个租户，登记簿写明；后续接入第二个应用前重新评估。

### 11.3 关键限制（实测，直接影响实现）

1. **REST 只支持 `public` schema**：`auth`、`storage` 与自定义 schema 不可经客户端 REST 访问；因此业务表一律落 `public` + `p068_` 前缀，不建自定义 schema。
2. **`auth.uid()` 可用**（`text`，等于 JWT `sub`），但**控制台 SQL 编辑器会误报 Supabase 语法**；SQL 的有效性以 REST 实测为准，不以编辑器报错判定失败。
3. **anon 读返回空集而非 403**：只带 Publishable Key 读到 `200 + []`。验收判据必须按「rows=0」而非状态码；同理 B 读 A、B 改 A、B 删 A 也表现为 200/204 + 0 行。
4. **`auth.users.id` 为 `VARCHAR(64)` 数字串**，不是 UUID：业务归属列用 `varchar(64)`（或 `text`）；本地 UUID 主键作业务 `record_id`，两者不混用、不做类型互推。
5. **补充事实**：`app/src/main/AndroidManifest.xml:9` 已声明 `INTERNET` 权限，§1 预检表中「无 INTERNET」已过时；README 中英两份已同批改写为「默认只在本机，主动登录并确认首传后才联网」（2026-11-10，见 `docs/risks.md` R13）。

结论：M1 放行条件满足（有 REST 请求、控制台用量、越权拒绝证据）；App 内登录与真机链路属 M3，不在本探针范围，不得据本条宣称 App 侧已通过。

## 12. 与草案的差异（2026-11-10 定稿）

| # | 草案原设定 | 定稿 | 原因与影响 |
|---|---|---|---|
| 1 | 为 P068 新建独立 PG 环境 | **共用 P059 现有免费环境**（用户已选） | 省成本；代价是额度/到期/误配为跨 APP 单点风险，必须在登记簿登记并在正式上线前复评跨 APP 隔离（同一 Auth 身份下 owner 规则只隔离用户，不隔离应用） |
